# Technical Specification: Authentication

## Technical Context

- **Backend**: FastAPI 0.115, Python, `python-dotenv` already in `requirements.txt`
- **Frontend**: React 19, Vite, plain `fetch` calls, no routing library, no state management library
- **No new production dependencies required**: FastAPI's `HTTPBearer` + Python stdlib `secrets` module suffice for token generation; React Context is built-in

---

## Implementation Approach

### Backend: Bearer-token middleware

1. On `POST /v2/auth/login`, validate `{username, password}` JSON body against `APP_USERNAME` / `APP_PASSWORD` environment variables; generate a cryptographically random token with `secrets.token_urlsafe(32)`; store it in a module-level in-memory set; return `{"token": "<value>"}`.
2. On `POST /v2/auth/logout`, remove the supplied token from the in-memory set.
3. A Starlette middleware (`api/middleware/auth.py`) intercepts every request. Requests to `POST /v2/auth/login` are allowed through. All other requests must carry `Authorization: Bearer <token>` with a valid in-memory token, or the middleware returns **HTTP 401** immediately—before any router handler runs.
4. Credentials are read from `config.py`'s new `AuthConfig` class. If `APP_PASSWORD` is empty the API logs a loud warning on startup (does not refuse to start, to allow graceful degradation in development).

Using middleware rather than per-router `Depends(...)` avoids touching every existing router file.

### Frontend: sessionStorage + LoginPage

1. Auth token is stored in `sessionStorage` so it is scoped to the browser tab (disappears on tab close).
2. A utility `react-app/src/utils/apiFetch.js` wraps `fetch`, automatically reading the token from `sessionStorage` and adding the `Authorization: Bearer` header. All components that call the API use `apiFetch` in place of `fetch`.
3. `App.jsx` holds a `token` state (seeded from `sessionStorage` on mount). When `token` is `null`/empty, it renders only `<LoginPage>`. Once authenticated it renders the full application.
4. `<LoginPage>` posts credentials to `POST /v2/auth/login`, stores the returned token in `sessionStorage` and lifts it to `App.jsx`.
5. A **Logout** button is added to `<header class="app-header">` in `App.jsx`. Clicking it calls `POST /v2/auth/logout`, clears `sessionStorage`, and resets `token` state to `null`.
6. `apiFetch` treats any **401** response as a session expiry: it clears `sessionStorage` and dispatches a custom `"auth:expired"` window event; `App.jsx` listens to that event and resets `token` to `null`.

## Data Model / API Changes

### New endpoints

```
POST /v2/auth/login
Body:  { "username": string, "password": string }
200:   { "token": string }
401:   { "detail": "Invalid credentials" }

POST /v2/auth/logout
Header: Authorization: Bearer <token>
200:   { "detail": "Logged out" }
```

### Auth token lifecycle

- Generated by `secrets.token_urlsafe(32)` on successful login
- Stored in a module-level `set[str]` in `api/routers/auth.py`
- Removed on logout
- All tokens are lost on server restart (no persistence; acceptable per requirements)

### Environment variables (additions to `.env.example`)

```
APP_USERNAME=admin
APP_PASSWORD=changeme
```

`APP_USERNAME` defaults to `"admin"` if unset; `APP_PASSWORD` has no default and triggers a startup warning if empty.

## Verification Approach

```bash
# Lint / typecheck (no type-checker configured; check via startup)
cd react-app && npm run build

# API smoke tests (existing test suite)
python -m pytest tests/

# Manual verification steps
# 1. Start API without APP_PASSWORD set → warning logged, server starts
# 2. GET /v2/satellites → 401
# 3. POST /v2/auth/login with wrong password → 401
# 4. POST /v2/auth/login with correct credentials → token returned
# 5. GET /v2/satellites with token → 200
# 6. POST /v2/auth/logout → 200; subsequent GET → 401
# 7. Frontend: open app → login screen shown
# 8. Frontend: login → full app shown
# 9. Frontend: logout → login screen shown
# 10. Frontend: close and reopen tab → login screen shown (sessionStorage cleared)
```
